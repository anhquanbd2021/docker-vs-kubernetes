Model guide

Layers, not alternatives — and when the top layer earns its keep

This demo exists because "Docker or Kubernetes?" frames two parts of one stack as competitors. The visualizer shows the shared half; the model scores where single-host machinery stops being enough.

A heuristic, not an oracle. The scorer encodes the article's argument as points. It will not surprise your architect — it is meant to make the reasoning visible, not replace it.

Feature one

The pipeline visualizer

Shared half

Identical up to the registry

Write code, write a Dockerfile, docker build, push the image to a registry — five steps that are byte-for-byte the same whether the target is one host or a fleet. The demo renders them once and feeds both paths from the same data.

Proves
Docker and Kubernetes are not alternatives. They are layers of the same pipeline.
Key detail
Kubernetes consumes the image Docker produces — the debate starts after the image exists.
The fork

Where the paths diverge

After the registry, the Docker path stays on one host — containers, networks, volumes, Compose. The Kubernetes path adds a control plane (API server, etcd, scheduler, controller manager), worker nodes (kubelet, runtime), and the objects you declare (Pods, Services, autoscaling).

Proves
What each side actually adds — components, not vibes.
Key detail
Imperative vs declarative: Docker answers commands; Kubernetes converges reality to a declared state.

Feature two

The decision model

Inputs

Describe the workload, not the tooling

Six knobs: services, hosts, replicas (availability), traffic pattern, deploy cadence, team size. Each maps to a specific thing orchestration buys you — discovery, placement, self-healing, autoscaling, rollouts, or the staff to run a control plane.

Scoring

Points pull toward the fleet

Every requirement adds points toward Kubernetes; a workload at or above the threshold earns its overhead. Under it, Docker/Compose is the correct amount of machinery — and the reasons list shows exactly which inputs tipped the balance.

Borderline calls
Within three points of the threshold the model says so — and recommends starting with Docker, since every image is already K8s-compatible.
Presets

The cautionary scenario

The three-person-startup preset — one service, one host, one replica — scores 1 of 30 and is flagged as over-engineered on Kubernetes: the control plane would cost more than the problem it solves. That is the article's opening story, made reproducible.

Run locally

Inspect the evidence

npm test        # model verdicts + pipeline structure + server routes
npm run prove   # one verdict line per preset workload
npm run check   # both
npm start       # serve the lab on :3000

The modules are plain ES modules — the same files the browser imports are the files the tests exercise.

Limits

What this demo does not claim

  • The scorer is a heuristic, not a capacity plan — it weighs six signals and ignores cost, compliance, data gravity, and managed-service options like ECS or Cloud Run.
  • "Docker path" means Docker/Compose on hosts you run — managed container platforms blur the line this model draws.
  • Pipeline stages are explanatory, not executable — nothing builds, runs, or schedules anything for real.
  • Numbers are transparent, not authoritative: the threshold is set so the article's own examples land where the article says they should.
  • All examples are fixtures. No real hostnames, IPs, or clusters appear anywhere.
